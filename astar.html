Informed Search Algorithm

A* Search — เดาทิศทางเป็น จึงหาเจอเร็วกว่า โดยยังได้ทางที่สั้นที่สุดเท่าเดิม

Dijkstra ค้นหาแบบ "แผ่คลื่นออกทุกทิศเท่า ๆ กัน" ซึ่งถูกต้องเสมอแต่เปลืองแรง เพราะมันไม่รู้เลยว่าปลายทางอยู่ทางไหน A* แก้ปัญหานี้ด้วยการเพิ่ม ค่าประมาณระยะที่เหลือ เข้าไป ทำให้การค้นหาเอนไปทางปลายทาง ผลคือสำรวจโหนดน้อยลงมาก แต่ยังรับประกันคำตอบที่สั้นที่สุดได้อยู่ ถ้าค่าประมาณนั้นมีคุณสมบัติที่ถูกต้อง

1. ทำไมต้องมี A*

ลองนึกว่าเราหลงอยู่ในโรงเรียนแล้วอยากไปห้องสมุด ถ้าใช้วิธีแบบ Dijkstra เราจะต้องเดินสำรวจทุกทิศโดยไล่จากที่ใกล้ตัวไปไกล จนกว่าจะบังเอิญเจอห้องสมุด ทั้งที่ในความเป็นจริงเรามองออกว่าห้องสมุดอยู่ทางขวามือ แล้วทำไมต้องเสียเวลาเดินไปทางซ้ายด้วย

ไอเดียของ A* ในประโยคเดียว

เวลาเลือกว่าจะสำรวจโหนดไหนต่อ อย่าดูแค่ "เดินมาไกลแค่ไหนแล้ว" แต่ให้ดู "เดินมาไกลแค่ไหนแล้ว + น่าจะเหลืออีกไกลแค่ไหน"

คำว่า "น่าจะเหลืออีกไกลแค่ไหน" คือค่าที่เราเดาเอา เรียกว่า heuristic (ฮิวริสติก) ในงานแผนที่มีตัวเดาที่ดีอยู่แล้วคือ ระยะเส้นตรง จากโหนดนั้นถึงปลายทาง ซึ่งวัดได้ทันทีจากพิกัด โดยไม่ต้องรู้ว่าทางเดินจริงเป็นอย่างไร

2. หัวใจคือสูตร f = g + h

f(n)  =  g(n)  +  h(n)

g(n) — ของจริงที่วัดแล้ว

ระยะสั้นที่สุดเท่าที่รู้ตอนนี้จากจุดเริ่มต้นมาถึงโหนด n ค่านี้คือตัวเดียวกับ dist ของ Dijkstra เป๊ะ ๆ ได้มาจากการบวกน้ำหนักจริงของเส้นทางที่เดินมา

h(n) — การเดาที่เหลือ

ค่าประมาณระยะจากโหนด n ไปถึงเป้าหมาย ในหน้านี้ใช้ ระยะเส้นตรง (วัดด้วยทฤษฎีบทพีทาโกรัสจากพิกัด x, y) คำนวณได้ทันทีโดยไม่ต้องค้นหาอะไรเลย

f(n) — คะแนนสำหรับจัดลำดับคิว

ประมาณการความยาวรวมของเส้นทางที่ดีที่สุดที่ผ่านโหนดนี้ A* จะหยิบโหนดที่ f น้อยที่สุดออกมาทำก่อนเสมอ

ถ้าให้ h = 0 จะเกิดอะไรขึ้น

f จะเหลือแค่ g ซึ่งก็คือ Dijkstra พอดี
พูดอีกอย่างคือ Dijkstra เป็นกรณีพิเศษของ A* ที่ "ไม่เดาอะไรเลย" ทั้งสองหน้านี้จึงใช้โค้ดชุดเดียวกันได้

ตัวอย่างค่าจริงจากกราฟตัวอย่างในหน้านี้

ที่รอบแรก A* ยืนอยู่ที่ S แล้วมองเห็นเพื่อนบ้าน 5 ตัว ค่าที่ได้เป็นดังนี้ (เป้าหมายคือ H)

3. heuristic ที่ดีต้องมีคุณสมบัติอะไร

การเดาไม่ได้แปลว่ามั่วได้ตามใจ ถ้าเดาผิดวิธี A* จะเร็วขึ้นก็จริงแต่คำตอบอาจไม่ใช่เส้นทางที่สั้นที่สุดอีกต่อไป คุณสมบัติที่ต้องการมีสองข้อ

① Admissible — ห้ามเดาเกินจริง (ข้อบังคับ)

h(n)  ≤  ระยะจริงที่สั้นที่สุดจาก n ถึงเป้าหมาย

ระยะเส้นตรงผ่านข้อนี้เสมอ เพราะไม่มีทางเดินไหนสั้นกว่าการบินตรง อย่างมากที่สุดก็เท่ากัน ถ้า h เดาเกินจริงเมื่อไหร่ A* อาจ "ตัดใจ" ทิ้งเส้นทางที่จริง ๆ แล้วดีที่สุดไป

② Consistent — เดาแล้วไม่ขัดกันเอง (ทำให้โค้ดง่ายขึ้น)

h(u)  ≤  w(u, v)  +  h(v)   สำหรับทุกเส้นเชื่อม

หมายความว่าเดินไปหนึ่งก้าวแล้วค่าประมาณต้องไม่ลดฮวบเกินกว่าระยะที่เดินไปจริง (เป็นรูปแบบหนึ่งของอสมการสามเหลี่ยม) ระยะเส้นตรงก็ผ่านข้อนี้เช่นกัน ผลดีคือเมื่อปิดโหนดไปแล้วไม่ต้องกลับมาเปิดใหม่ (no re-opening) โค้ดจึงเรียบง่ายเท่ากับ Dijkstra

ถ้า h แรงเกินไป

การคูณ h ให้ใหญ่ขึ้น (เช่น h × 2) จะทำให้ค้นหาเร็วขึ้นอีก แต่หลุดเงื่อนไข admissible จึงไม่รับประกันคำตอบที่สั้นที่สุดอีกต่อไป — ได้ทางที่ "ใช้ได้" แต่ไม่ใช่ "ดีที่สุด" เทคนิคนี้เรียกว่า weighted A* ซึ่งบางเกมใช้เพื่อแลกความแม่นยำกับความเร็ว ส่วนถ้าสุดโต่งจนดูแต่ h อย่างเดียว (ทิ้ง g) จะกลายเป็น greedy best-first search ที่เร็วมากแต่หลงทางง่าย

4. Pseudo code และภาพจำลองที่กดเดินได้

โครงสร้างเหมือน Dijkstra เกือบทั้งหมด ต่างกันแค่ค่าที่ใช้จัดลำดับในคิวเปลี่ยนจาก g เป็น f = g + h (บรรทัดที่ 3, 16, 17) ในภาพจะเห็นเส้นประสีเหลืองลากจากโหนดที่กำลังพิจารณาไปยังเป้าหมาย นั่นคือค่า h ของโหนดนั้น

  1. ฟังก์ชัน AStar(กราฟ G, จุดเริ่ม s, เป้าหมาย t, ฟังก์ชันประมาณ h):
  2. g[s] ← 0 // ระยะจริงที่เดินมา
  3. f[s] ← g[s] + h(s, t) // ค่าจัดลำดับคิว
  4. open ← คิวลำดับความสำคัญ, ใส่ s ด้วยค่า f[s]
  5. closed ← เซตว่าง // โหนดที่ปิดแล้ว
  6. ขณะที่ open ยังไม่ว่าง:
  7. u ← โหนดใน open ที่ f น้อยที่สุด (ดึงออกมา)
  8. ถ้า u = t : คืนค่า เส้นทางที่ย้อนรอยจาก prev
  9. เพิ่ม u เข้า closed
  10. สำหรับทุกเพื่อนบ้าน v ของ u:
  11. ถ้า v อยู่ใน closed : ข้ามไปตัวถัดไป
  12. alt ← g[u] + w(u, v)
  13. ถ้า alt < g[v] : // relaxation
  14. g[v] ← alt
  15. prev[v] ← u
  16. f[v] ← g[v] + h(v, t) // ต่างจาก Dijkstra
  17. ใส่ v ลง open ด้วยค่า f[v] (หรืออัปเดตค่าเดิม)
  18. คืนค่า "ไม่พบเส้นทาง"
ลองเปรียบเทียบเอง

เปิดภาพจำลองของ Dijkstra ไว้อีกแท็บ แล้วกดเล่นพร้อมกัน จะเห็นชัดว่า Dijkstra วิ่งไปทางซ้าย (P, Q) ตั้งแต่ต้น ส่วน A* ไม่แตะสองโหนดนั้นเลยแม้แต่ครั้งเดียว

5. เดินทีละขั้นด้วยมือ

ทำไมหยุดตอนดึง H ออกมาได้เลย

ตอนจบรอบที่ 6 คิวมี H:525, D:530, G:531, P:684, Q:686 ค่า f ของ H น้อยที่สุด และเพราะ h ไม่เคยเดาเกินจริง ค่า f ของโหนดอื่น ๆ จึงเป็น "ราคาต่ำสุดที่เป็นไปได้" ของเส้นทางที่ผ่านโหนดนั้น เมื่อทุกตัวมีราคาขั้นต่ำมากกว่า 525 อยู่แล้ว ก็ไม่มีทางไหนที่จะดีกว่า 525 ได้อีก จึงหยุดได้อย่างมั่นใจ

นี่คือเหตุผลที่ admissible สำคัญ

ถ้า h เดาเกินจริงแม้แต่นิดเดียว ตรรกะข้างบนจะพัง เพราะโหนดที่ดูเหมือน "แพงเกิน 525" อาจซ่อนเส้นทางที่จริง ๆ แล้วถูกกว่าไว้ — A* จะหยุดเร็วเกินไปแล้วคืนคำตอบที่ไม่ใช่ทางที่สั้นที่สุด

ข้อควรจำ

A* ไม่ได้ "ฉลาดกว่า" Dijkstra ในเชิงคุณภาพคำตอบ — คำตอบเหมือนกันทุกประการ สิ่งที่ต่างคือปริมาณงานระหว่างทางเท่านั้น และ A* จะเก่งได้ก็ต่อเมื่อมี h ที่ดีให้ใช้ ถ้าไม่มีข้อมูลพิกัดหรือประมาณระยะไม่ได้เลย ก็ต้องกลับไปใช้ Dijkstra

7. ใช้ในโปรเจกต์นี้อย่างไร

A* เป็นอัลกอริทึมค่าเริ่มต้นของเว็บแผนที่นี้ อยู่ในเมธอด shortestPath() ของไฟล์ js/graph.js ส่วน heuristic อยู่ในเมธอด heuristic() ไฟล์เดียวกัน

heuristic ของอาคารหลายชั้น

แผนที่จริงเป็น 3 มิติ เพราะมีการขึ้นลงระหว่างชั้น ค่า h จึงเป็นระยะเส้นตรงแบบ 3 มิติ โดยแปลงหมายเลขชั้นเป็นความสูงจริงก่อน (ชั้นละ 3.8 เมตร)

h  =  √( Δx² + Δy² + (Δชั้น × 3.8)² )

เมื่อผู้ใช้เลือกเกณฑ์ "เวลาน้อยสุด"

ถ้าน้ำหนักของเส้นเชื่อมเป็นวินาที ค่า h ที่เป็นเมตรจะเทียบกันไม่ได้ ต้องแปลงหน่วยให้ตรงกันก่อน โดยหารด้วยความเร็วเดินสูงสุดที่เป็นไปได้ (1.45 เมตร/วินาที) การใช้ความเร็วสูงสุดเป็นตัวหารทำให้ค่าที่ได้เป็นเวลาที่น้อยที่สุดเท่าที่เป็นไปได้ จึงยังไม่เกินค่าจริง = ยังเป็น admissible อยู่

hเวลา  =  ระยะเส้นตรง 3 มิติ  ÷  1.45   (วินาที)
รายละเอียดที่ผิดกันบ่อยในโหมดเวลา

ถ้าเผลอหารด้วยความเร็วเฉลี่ย (1.3) แทนความเร็วสูงสุด ค่า h จะสูงกว่าความจริงในบางเส้นทาง กลายเป็นเดาเกินจริงและอาจได้เส้นทางที่ไม่ใช่เร็วที่สุด นี่คือเหตุผลที่ค่าคงที่ MAX_SPEED ใน js/graph.js ตั้งไว้สูงกว่าความเร็วเดินที่ใช้คำนวณเวลาจริง

  • Binary heap (คลาส MinHeap) แทนคิวแบบไล่หาทีละตัว
  • Lazy deletion — แทนที่จะไล่แก้ค่าเดิมในคิว จะใส่รายการใหม่ทับลงไปแล้วข้ามรายการเก่าที่เจอทีหลัง ซึ่งง่ายกว่าและเร็วกว่าในทางปฏิบัติ
  • ตัวกรองเส้นเชื่อม — ตัวเลือกอย่าง "เลี่ยงบันได" ทำงานตอน relax คือข้ามเส้นเชื่อมที่ไม่อนุญาตไปเลย โดยไม่ต้องสร้างกราฟใหม่
  • สถิติการทำงาน — เก็บจำนวนโหนดที่สำรวจ (visited) และจำนวนครั้งที่ relax เพื่อแสดงผลเทียบกันได้ระหว่าง A* กับ Dijkstra
ลองเองได้

เปิดหน้าแผนที่ 3 มิติ เลือกเส้นทางข้ามอาคาร แล้วสลับช่อง "อัลกอริทึม" ดูตัวเลขจำนวนโหนดที่สำรวจในผลลัพธ์ ยิ่งจุดเริ่มต้นกับปลายทางอยู่ไกลกัน ส่วนต่างจะยิ่งชัด

ย้อนกลับไปอ่าน Dijkstra's Algorithm → รากฐานของ A* — เข้าใจ relaxation และเหตุผลที่การเลือกค่าน้อยสุดก่อนทำให้คำตอบถูกต้องเสมอ กลับไป แผนที่กราฟ 3 มิติ → ทดลองค้นหาเส้นทางบนกราฟจริงของอาคารเรียน พร้อมสลับอัลกอริทึมได้

ภาพจำลองในหน้านี้รันอัลกอริทึมจริงในเบราว์เซอร์ ไม่ได้เป็นภาพที่อัดไว้ล่วงหน้า โค้ดอยู่ที่ js/learn-viz.js ส่วนอัลกอริทึมที่ใช้งานจริงอยู่ที่ js/graph.js
